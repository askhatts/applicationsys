# Система заявок на ремонт и обслуживание

Веб-приложение для КГП «Центр ядерной медицины и онкологии»: подача заявок на
поломки/ремонт (медтехника, компьютеры, электрика, кондиционеры и вентиляция,
ремонт помещений) по отделам, контроль сроков, подтверждение исполнения
заявителем и дэшборд-мониторинг.

Работает во внутренней сети без доступа в интернет: Flask + SQLite + Waitress,
все статические файлы (включая Chart.js) — локальные. Также разворачивается
на публичном поддомене (см. «Развёртывание на VPS» ниже) — в этом случае
обязательно прочитайте раздел «Публичный доступ: на что обратить внимание».

## Возможности

- **Подача заявки без пароля**: сотрудник выбирает отдел (36 подразделений),
  категорию, приоритет, описывает проблему. Дата подачи фиксируется
  автоматически, срок исполнения ставится по приоритету:
  Аварийная — 4 ч, Срочная — 24 ч, Обычная — 72 ч, Плановая — 168 ч
  (настраивается в админке).
- **Код отслеживания**: после подачи заявитель получает ссылку/код, по которому
  видит статус и подтверждает исполнение («Подтверждаю» / «Вернуть в работу»).
- **Кабинет исполнителя** (по логину/паролю): каждая служба видит только свои
  заявки. Принять (можно скорректировать срок с указанием причины), отметить
  выполненной («что сделано» обязательно), отклонить с причиной.
- **Полная история** каждой заявки: кто, когда, что сделал, все переносы сроков.
- **Дэшборд**: счётчики (новые/в работе/просрочено/подтверждено/возвраты),
  графики по отделам, службам, категориям, динамика за 30 дней; просроченные —
  красным, близкие к сроку — жёлтым. Ссылка «только просмотр» для руководства
  (без входа). Экспорт CSV/Excel.
- **Админка**: справочники (отделы, службы, категории → службы, приоритеты и
  SLA), пользователи, настройки.

## Быстрый старт (машина с интернетом)

```bat
py -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python manage.py init-db
.venv\Scripts\python run.py        &rem http://127.0.0.1:5000
```

`init-db` выводит пароль администратора (логин `admin`) и ссылку-ключ дэшборда —
сохраните их.

## Развёртывание на сервере БЕЗ интернета

На машине с интернетом уже подготовлена папка `deploy\wheels` (все зависимости,
подходят для Python 3.12–3.14, 64-бит). Если её нужно обновить:
`pip download -r requirements.txt -d deploy\wheels`.

1. Скачайте с python.org установщик **Python 3.12–3.14 (64-bit)** и перенесите
   на сервер вместе с папкой проекта (целиком, с `deploy\wheels`).
2. Установите Python (отметьте галочку **Add python.exe to PATH**).
3. В папке проекта:

```bat
py -m venv .venv
.venv\Scripts\pip install --no-index --find-links deploy\wheels -r requirements.txt
.venv\Scripts\python manage.py init-db
```

4. Запуск: `run_prod.bat` (порт 8080). Проверьте с другого компьютера:
   `http://IP-сервера:8080`.
5. Откройте порт в брандмауэре Windows (от имени администратора):

```bat
netsh advfirewall firewall add rule name="Заявки на ремонт" dir=in action=allow protocol=TCP localport=8080
```

6. **Автозапуск**: Планировщик заданий Windows → Создать задачу →
   триггер «При запуске системы» → действие: запуск `run_prod.bat`
   (рабочая папка — папка проекта) → «Выполнять вне зависимости от входа
   пользователя».
7. **Бэкап**: `backup_db.bat` кладёт копию БД в `backups\` — добавьте его в
   Планировщик (например, ежедневно ночью). Вся база — один файл
   `instance\app.db`.

## Развёртывание на VPS (публичный поддомен)

Два готовых сценария в `deploy/linux/` — выберите по ситуации на сервере.

### Вариант А: сервер уже занят Docker-стеком с Caddy (наш случай)

Если на VPS уже работает другой проект в Docker с Caddy на портах 80/443
(так и есть на боевом сервере `oncomap-abai.kz` — там свой backend + Caddy),
ставить nginx нельзя — порты заняты. Вместо этого наше приложение поднимается
отдельным Docker-контейнером в существующей сети `deploy_default`, а в конец
их `Caddyfile` дописывается один site-блок для `requests.oncomap-abai.kz`.
Существующий проект (`deploy-backend-1`, `deploy-caddy-1`) не трогается и не
перезапускается — только «мягкая» перезагрузка конфига Caddy (`caddy reload`,
без даунтайма).

```bash
git clone https://github.com/askhatts/applicationsys.git /opt/applicationsys
bash /opt/applicationsys/deploy/linux/setup_docker.sh
```

Что делает скрипт: собирает образ (`Dockerfile` в корне репозитория),
запускает контейнер `requests_app` (порт 8000 виден только внутри
`deploy_default`, наружу не публикуется), дописывает блок из
`deploy/linux/caddy-site-block.conf` в `/opt/onco/deploy/Caddyfile` (с
резервной копией файла перед изменением) и делает `caddy reload`. Caddy сам
получит сертификат Let's Encrypt для нового поддомена, как только DNS
обновится — ничего дополнительно перезапускать не нужно.

Обновление после изменений в репозитории:
```bash
cd /opt/applicationsys && git pull && \
  docker compose -f deploy/linux/docker-compose.requests.yml up -d --build
```
Логи: `docker logs -f requests_app`.

### Вариант Б: чистый сервер, порты 80/443 свободны

```bash
git clone https://github.com/askhatts/applicationsys.git /tmp/appsys-src
bash /tmp/appsys-src/deploy/linux/setup_vps.sh
```
Скрипт ставит зависимости, клонирует репозиторий в `/opt/applicationsys`,
создаёт venv, инициализирует БД, поднимает systemd-службу `applicationsys`
(waitress на 127.0.0.1:8000), настраивает nginx-реверс-прокси и получает
сертификат через certbot.

Бэкап (для обоих вариантов): `deploy/linux/backup_db.sh` в cron.
Обновление (вариант Б): `deploy/linux/update.sh`.

### DNS (обязательно для обоих вариантов)

В панели домена (gohost.kz → «Домены» → DNS-записи) добавьте A-запись
`requests` → IP вашего VPS. Проверить: `dig +short requests.oncomap-abai.kz`
должен вернуть IP сервера. Без этого сертификат Let's Encrypt не выпустится.

### Публичный доступ: на что обратить внимание

Приложение изначально спроектировано для внутренней сети, где форма подачи
заявки открыта без пароля — это осознанно (минимум трения для сотрудников).
При выходе на публичный домен это означает, что заявку сможет подать кто
угодно из интернета. Рекомендации, если это важно:

- Ограничить частоту подачи по IP на уровне nginx (`limit_req_zone`).
- Добавить простую защиту от ботов (например, скрытое honeypot-поле в форме).
- Держать поддомен «непубличным» — не размещать ссылку на него на основном
  сайте, делиться адресом только с сотрудниками (защита через безвестность,
  не замена настоящей аутентификации, но снижает случайный/автоматический спам).
- Данные заявителей (ФИО, контакты) в БД — рассмотреть, нужно ли ограничить
  доступ к `/dashboard`-ключу и `/export.*` более тщательно (например, сменить
  ключ сразу после развёртывания через `manage.py regen-dashboard-token`).

## Служебные команды

```bat
.venv\Scripts\python manage.py init-db [--force]      &rem пересоздать БД (удаляет данные!)
.venv\Scripts\python manage.py create-user ЛОГИН "ФИО" "Название службы"
.venv\Scripts\python manage.py create-admin ЛОГИН ["ФИО"]
.venv\Scripts\python manage.py set-password ЛОГИН
.venv\Scripts\python manage.py regen-dashboard-token
```

Пользователей также можно создавать в админке (`/admin/users`).

## Роли и доступ

| Кто | Как входит | Что может |
|---|---|---|
| Заявитель | без входа | подать заявку; по коду — отслеживать и подтверждать/возвращать |
| Исполнитель | логин/пароль | заявки своей службы: принять, перенести срок (с причиной), выполнить, отклонить |
| Администратор | логин/пароль | всё: все заявки, дэшборд, справочники, пользователи |
| Руководство | ссылка с ключом | дэшборд только для просмотра + экспорт |

## Как считаются сроки

Срок = дата подачи + SLA-часы приоритета (календарные часы, без учёта выходных —
осознанное упрощение; часы можно менять в админке). Просроченной считается
открытая заявка (новая/в работе), у которой срок в прошлом. «Срок истекает» —
осталось меньше четверти SLA (доля настраивается). Отдельно на дэшборде виден
счётчик «выполнено с опозданием» (закрыта позже срока) и «возвраты в работу».

## Структура проекта

```
app/                 код приложения (Flask, blueprints)
  schema.sql         схема БД (8 таблиц)
  seed.py            справочники: 36 отделов, службы, категории, приоритеты
  services.py        переходы статусов + история (единая точка)
  deadlines.py       расчёт просрочки
  templates/, static/  шаблоны и статика (Chart.js — локально, без CDN)
instance/            app.db (база), config.py (SECRET_KEY) — не копировать между серверами
deploy/wheels/       зависимости для офлайн-установки
tools/smoke.py       сквозной автотест (запускается против работающего сервера)
manage.py            служебные команды
run.py / run_prod.bat  запуск: разработка / сервер
backup_db.bat        резервная копия БД
```

## Жизненный цикл заявки

```
Новая → В работе → Выполнена → Подтверждена (заявителем)
  ↓         ↓          ↓ «не выполнено»
Отклонена ←┘          → В работе (возврат, причина в истории)
```
